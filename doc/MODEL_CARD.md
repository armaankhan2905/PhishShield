# PhishShield model card

Two small models support the rule-based detection engine. Neither decides a
verdict on its own: their scores enter the evidence-gated scoring
(`src/detection/fuse.py`). A message can't be rated **phishing** on a model
score alone. Every number below is generated by `python -m src.eval.phish_bench`
and stored in `data/eval.json` (test) or `data/calibration.json` (validation).

## Models

| | URL model | Text model |
|---|---|---|
| Version | `url-hgb-1` | `text-tfidf-lr-1` |
| File | `models/url_model.joblib` (1.3 MB) | `models/text_model.joblib` (2.9 MB) |
| Method | Gradient-boosted trees (scikit-learn `HistGradientBoostingClassifier`) on 54 lexical features | TF-IDF word 1–2-grams (150k vocabulary) + logistic regression (C chosen on validation) |
| Input | The URL text only, with scheme and leading `www.` removed. **Nothing is fetched** | Message text with links → `zurlz`, emails → `zemailz`, digits → `0` |
| Output | Calibrated probability (isotonic, fitted on validation) | Same |
| Used when | Every link in a message | Messages with ≥ 3 words (not bare URLs) |
| Points in the score | 0 below p = 0.70, up to 45 at p = 1.0 | 0 below p = 0.50, up to 45 at p = 1.0 |
| Training time (CPU) | ~35 s | ~90 s |
| Speed in the full engine | 2–13 ms per message, all layers included (see `data/eval.json` → `run.ms_per_item`) | |

Load with **scikit-learn 1.6.1** (pinned in both requirements files). If a model
file is missing or fails to load, the engine reports that layer as
`unavailable` / `failed` and lowers `confidence`; it never treats a missing
model as evidence of safety.

**Splits (`src/model/prepare.py`):**
- 70 / 15 / 15 by a fixed hash.
- URLs are grouped by **registered domain**; texts by a **near-duplicate key** (first 30 normalised words) after de-duplication.
- Messages that appear with both labels are dropped.

**Checked:**
- 0 of 123,905 registered domains and 0 of 20,733 texts appear in more than one split.
- No test-only URL domain was seen in training or validation.
- Rebuilding the data twice gives byte-identical files.

## Results on held-out data

Positive = **flagged** (suspicious or phishing, score ≥ 30). The **system** column
is the full product: rules + both models + scoring. Run twice with identical
results (`metrics_sha256 = 9b5ff4ec33237882`).

| Test set | n | System P | System R | System F1 | System FPR | Model alone F1 / FPR | Old 35/30/35 formula F1 / FPR |
|---|---|---|---|---|---|---|---|
| Emails | 2,543 | 0.925 | 0.956 | **0.941** | 4.5% (72) | text 0.972 / 1.9% | 0.956 / 3.3% |
| SMS | 424 | 1.000 | 0.622 | **0.767** | 0.0% (0) | text 0.908 / 7.3% | 0.916 / 4.05% |
| URLs (fixed 6,000 sample) | 6,000 | 0.978 | 0.607 | **0.749** | 0.8% (30) | URL 0.837 / 6.1% (all 31,767) | 0.805 / 1.8% |
| OpenPhish (recent, unseen domains) | 276 | 1.000 | 0.685 | 0.813 | n/a | URL 0.913 | 0.871 |
| Tranco top sites (benign) | 4,089 | n/a | n/a | n/a | **0.8%** (33) | URL FPR 5.6% | 1.5% |
| UCI SMS ham (unseen source) | 3,630 | n/a | n/a | n/a | **0.03%** (1) | text FPR 9.5% | 5.5% (198) |
| UCI SMS spam (spam ≠ phishing, information only) | 151 | 1.000 | 0.755 | 0.860 | n/a | text 0.973 | 0.966 |
| Hand-written Indian set (synthetic) | 36 | 1.000 | 1.000 | 1.000 | 0.0% | text 0.941 / 10% | 0.970 / 5% |

**How to read this:**
- **Fewer false alarms, by design.** The scoring gives up some recall to keep false alarms low.
  - The old 35/30/35 formula catches more SMS (F1 0.92 vs 0.77), links (0.81 vs 0.75) and recent phishing (0.87 vs 0.81).
  - But it raises about twice as many false alarms on links (1.8% vs 0.8%) and popular sites (1.5% vs 0.8%), and **198** false alarms on ordinary SMS where the system raises **1**.
  - That's the trade-off the revised plan asked for. Lowering `SAFE_BELOW` or raising `ML_MAX` moves along it.
- **Low "phishing"-level recall is expected.** A **phishing** verdict needs proven technical evidence (look-alike domain, sender mismatch, link-text mismatch, a request for details sent to a domain the brand doesn't own). Dataset rows rarely carry it: there are no headers, and many links were stripped. Phishing-level precision is 0.90–1.00 on every set.
- **Rules alone catch little on these datasets** (F1 ≤ 0.11). The datasets lack the sender and link context the rules look at. The rules matter most on real messages; on the hand-written set they alone reach F1 0.97.

**Validation (chosen scoring setting, `data/calibration.json`):**
- Texts: precision 0.946, recall 0.884, false alarms 3.2%.
- URLs: precision 0.985, recall 0.646, false alarms 0.9%.

## How the scoring was tuned

`python -m src.eval.phish_bench --tune` searched 108 combinations on the **validation split**:
- `ML_MAX` ∈ {35, 45, 55}
- `URL_FLOOR` ∈ {0.7, 0.8, 0.9, 0.95}
- `TEXT_FLOOR` ∈ {0.5, 0.7, 0.85}
- `SAFE_BELOW` ∈ {30, 35, 40}

Selection rule:
1. Keep only combinations with false alarms ≤ 5% on both validation messages and URLs.
2. Maximise the mean F1 of the two.
3. Treat differences under 0.005 as ties, and pick the tied setting closest to the previous defaults.

Chosen: `ML_MAX = 45`, `URL_FLOOR = 0.7`, `TEXT_FLOOR = 0.5`, `SAFE_BELOW = 30`. The heuristic weights and caps are still hand-set.

## Limitations and biases

- **English only.** No Hindi, Hinglish or other Indian-language messages in training or rules.
- **Old, Western email data.** The emails are mostly 2000s Enron / SpamAssassin; the SMS ham is largely UK. Modern Indian SMS were represented only by **synthetic templates**, which fixed a severe problem: before them, the text model rated real-format bank alerts 0.96–1.00 phishing.
  - Templates and the hand-written test set were written by the same author, so results on that set are optimistic even after removing the 4 exact matches.
  - **Real, redacted messages collected by the team are still needed.**
- **Spam vs phishing.** Several sources label marketing spam as positive. The text model partly learns "spam", not only "phishing".
- **URL model sees spelling only.** It never visits a page, checks domain age or uses reputation lists. Popular bare domains are its weak spot (5.6% false alarms alone; 0.8% after scoring).
- **SMS vs email labels were inferred.** The combined corpus doesn't label them, so `prepare.infer_kind` guesses from length and the email corpus's pre-tokenised formatting. Some rows will be wrong.
- **Datasets age quickly.** OpenPhish results show how the models handle phishing collected today; other numbers come from older corpora.

## Changes made after seeing test results (disclosed)

0. **Old-formula comparison fixed in Phase 5.** The 35/30/35 comparison used to treat the text model as "scored 0" for a bare link (there is no wording to read), which made the old formula look far worse on links (F1 0.12). It now skips that layer for links, as the formula intends. Only the comparison column changed; the system's own numbers are identical.


1. **SMS/email labelling was corrected after the first test run.** The original rule (≤ 300 characters = SMS) put short spam emails in the SMS set.
   - First-run test numbers: SMS F1 0.486, email F1 0.944, URLs F1 0.749.
   - Validation tuning was redone after the fix and chose the same constants. The models were not retrained; labels don't affect training.
2. **Detection logic changes:**
   - SMS short codes and spaced phone numbers count as something to act on;
   - "share your OTP with …" counts as something to act on.

   These were prompted by validation analysis and by the hand-written set, not tuned on the test split.
3. **4 hand-written test scams were removed** because they matched synthetic training templates.

## Reproduce

```bash
python -m src.model.fetch_data && python -m src.model.prepare
python -m src.model.train_url && python -m src.model.train_text
python -m src.eval.phish_bench --tune   # validation; copy "chosen" into src/detection/fuse.py
python -m src.eval.phish_bench          # test; writes data/eval.json
```
